# 開源推廣 Issue 草稿

GitHub connector 建立 issue 回傳 403；以下尚未建立於 GitHub。

## [P1][Product] 明確產品定位、目標使用者與 README 採用理由

### 問題與目的

目前 README 以使用教學為主，開發者尚難快速判斷 Agentin 解決什麼問題，以及何時值得導入。

### 建議範圍

- 定義主要使用者與首版核心場景；首頁說明整合 CLI agent、模型 API、函式／MCP 工具的价值。
- 說明共同事件、取消、逾時與清理介面如何減少宿主整合工作。
- 提供適用／不適用場景，以及直接使用單一 runtime 的選擇依據。
- 釐清現有 SDK 與 #20／#26 Slack 接入提案的產品關係，避免尚未完成能力被描述為現有功能。

### 驗收條件

- [ ] README 開頭能回答給誰用、解決什麼問題、為何採用。
- [ ] 包含最小範例、功能狀態與下一步文件連結。
- [ ] 提供英文首頁或英文入口，保留繁體中文文件。

## [P1][Release] 定義公開 API、experimental 範圍與版本相容政策

### 問題與目的

SDK 轉匯出部分 Engine／Hub 型別；外部使用者需要知道可依賴的介面與升級風險。

### 建議範圍

- 盤點公開 exports、型別與底層依賴，定義支援的公開入口。
- 區分穩定、alpha 與 experimental 能力；明確標示 Codex adapter 現況。
- 訂定版本、breaking change、棄用與遷移政策，說明 0.x 期間承諾。
- 與 #7 套件交付、#12 runtime 契約銜接。

### 驗收條件

- [ ] 公開 API 清單與支援狀態可查閱。
- [ ] 重大變更有 changelog 與遷移說明規則。
- [ ] 使用者不需依賴未承諾的內部路徑即可完成基本整合。

## [P1][Maintenance] 建立 CI、貢獻指南與開源維護流程

### 問題與目的

目前工作目錄未見 .github 工作流程、CONTRIBUTING、SECURITY 與 CHANGELOG；外部貢獻及問題回報缺少一致入口。

### 建議範圍

- 建立乾淨環境的安裝、建置與無模型測試 CI；真實模型驗收獨立明確啟用。
- 加入 bug／feature issue 模板與適量 PR 檢查項。
- 提供 CONTRIBUTING：開發設定、模組責任、必要檢查與提交流程。
- 提供 SECURITY 與可實際使用的非公開通報方式。
- 建立 CHANGELOG 與發布檢查流程，說明維護者及支援方式。

### 驗收條件

- [ ] PR 可看到可重現的 CI 結果。
- [ ] 外部貢獻者能依文件完成設定及必要檢查。
- [ ] 問題回報包含版本、runtime、重現步驟與遮罩後診斷。
- [ ] 發布紀錄與漏洞通報入口可查閱，不承諾尚無能力提供的 SLA。

## [P1][Docs] 整理 runtime 權限、資料流與取消保證

### 問題與目的

限制分散在文件中；開發者需能判斷權限與資料處理邊界，才敢把 SDK 嵌入產品。

### 建議範圍

- 整理 runtime 權限矩陣：shell、讀檔、寫檔、Hub 允許清單、直接 MCP 與 OS 隔離。
- 說明 API key、prompt、工具參數、事件、產物經過哪些程序／端點及儲存位置；區分預設與可選行為。
- 說明取消／逾時的合作式工具限制、cleanup unconfirmed 與副作用未確認情境。
- 區分執行成功、輸出 schema 通過與業務驗收成功。
- 連結 #8 真實驗收及 #12 能力矩陣，未驗證項目明確標示。

### 驗收條件

- [ ] 有集中且可由 README 到達的信任與限制文件。
- [ ] 各項保證有對應實作或驗收依據；未知項目不宣稱支援。
- [ ] 提供安全處理憑證及敏感日誌的設定範例，不放入真實秘密。

## [P2][Adoption] 外部開發者試用與首次成功體驗驗證

### 問題與目的

內部範例可跑通，仍不足以證明外部開發者能自行整合並有持續使用理由。

### 建議範圍

- 招募 3–5 位未參與開發的使用者，明確記錄其場景；本單不授權自動對外邀請或發訊息。
- 使用 #7 發行產物及 #10／#26 或收斂的唯讀案例進行試用。
- 記錄安裝到首次成功時間、卡點、維護者協助次數與採用／放棄原因。
- 採同意的回饋或人工紀錄，不預設加入遙測。
- 將主要卡點轉為可追蹤修正，據證據調整定位與下一版優先級。

### 驗收條件

- [ ] 完成 3–5 份試用紀錄與問題彙整。
- [ ] 以 10 分鐘首次成功為目標並記錄實際結果，不用下載數取代整合成功。
- [ ] 確認至少一個願意持續使用的具體場景；未成立時記錄原因與下一步。
- [ ] 發布前主要導入阻礙已修正或明確揭露。
